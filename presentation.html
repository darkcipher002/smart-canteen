00 / THE BRIEF

The queue was the problem.

A Hotel at peak hour runs on paper tickets, shouted order numbers, and a cashbox that has to be reconciled by hand at closing. Nobody — not the customer, not the kitchen, not the person running the till — can see the same picture of what's happening at the same time.

So we built one shared source of truth.

This hotel OS is four purpose‑built screens — customer, admin, waiter, and account access — all reading and writing the same live database. An order placed on a phone in the queue is visible in the kitchen a moment later, and visible to the customer again the moment it's approved. No refreshing, no shouting.

June Wema Bobo

FRONT DOOR — ACCOUNTS & ACCESS

login.html register.html

LIVE DEMO — DO THIS ON STAGE

  1. Register a brand‑new account on register.html and show the password‑match / minimum‑length checks firing before Firebase is even called.
  2. Show the new account appear in Firestore under users with role: "customer" and a server timestamp.
  3. Log out, then log back in on login.html; toggle Remember me and explain what changes.
  4. Type a wrong password on purpose — show the friendly error instead of a raw Firebase error code.

EXPLAIN THIS

  • Firebase Authentication owns the password — the app never sees or stores it, only Firebase's SDK does (createUserWithEmailAndPassword / signInWithEmailAndPassword).
  • Sign‑up is two writes, not one: an Auth account for identity, plus a Firestore document for everything else (role, status, join date) — because Auth can't store custom fields.
  • setPersistence() chooses between browserLocalPersistence (stays signed in) and browserSessionPersistence (forgets on tab close) — that's what the "Remember me" box actually controls.
  • Errors are caught and mapped to plain English (auth/invalid-credential, auth/email-already-in-use) instead of exposing Firebase's internal codes to the user.
LIKELY QUESTION FROM THE PANEL

"What stops a customer from editing the page to make themselves an admin?"

The role field lives in Firestore, not in the browser, and it's only ever set once — at sign‑up, to "customer" — by code the user can't rewrite from dev tools. Promoting someone to a staff role is a deliberate action taken from the admin panel, not a value the client can hand itself. The next hardening step we'd add is Firestore Security Rules that reject any write to role that doesn't come from an already‑privileged account.

02

Esther Girl

THE COUNTER — ORDERING & PAYMENT

dashboard.html

LIVE DEMO — DO THIS ON STAGE

  1. Search and filter the menu by category, add two or three items to the cart, and open the cart panel.
  2. Pick a delivery point on the map, choose Pay Now with Paystack, and complete a test payment.
  3. Immediately switch to the Admin ticket's screen (or a second tab) so the audience sees the same order appear there in real time, with no refresh.
  4. Once it's approved by admin, show the status pill on the customer side flip from Pending Approval to Preparing Your Food live.
  5. Show a past delivered order and leave a star rating / review.

EXPLAIN THIS

  • The order tracker isn't polling — it's a live onSnapshot() listener on that customer's own orders, so Firestore pushes the update the instant admin changes it.
  • Paystack's popup is a self‑contained widget: it collects card/M‑Pesa details itself, so this page never touches raw payment details.
  • On success, handlePaystackSuccess() tries to confirm the charge server‑side (see Mark's ticket), then finalizeOrder() writes the order to Firestore either way — payment confirmation and order creation are two separate, deliberate steps.
  • Reviews are only unlocked once an order's status is Delivered, so ratings reflect real completed orders.
LIKELY QUESTION FROM THE PANEL

"What if Paystack says the payment succeeded but the connection drops before it's verified?"

The order is still created — we never want a customer who genuinely paid to lose their order — but it's saved with the status "Paid (Unverified – check admin panel)" instead of a clean "Paid". That's a deliberate fallback: the system stays usable even if the verification function is briefly unreachable, and admin can reconcile the flagged ones by hand. It's a small example of designing for failure instead of assuming the happy path.

Abby Girl

BACK OF HOUSE — ADMIN COMMAND CENTRE

admin.html

LIVE DEMO — DO THIS ON STAGE

  1. Approve Esther's incoming order, then dispatch it — narrate the status pulsing on the "Pending" card first.
  2. Open the menu/inventory tab and add or edit a menu item live; show it appear instantly on the customer's menu.
  3. Open the waiters tab, show auto‑assign balancing load across waiters, then add a delivery point on the map.
  4. Open the loyalty tab and show a customer's tier update from completed orders.
  5. Jump to Analytics and export the day's report as a PDF with one click.

EXPLAIN THIS

  • Every panel here — orders, menu, waiters, delivery points, loyalty, analytics — is a live onSnapshot() view onto the same Firestore collections everyone else's screen also uses.
  • Auto‑assign picks the waiter with the lowest current order load, not a fixed rotation — it's a small load‑balancing algorithm, not a coin flip.
  • Every action here (menu edit, waiter added, delivery point placed) is a normal Firestore write — there's no separate "admin API"; permission comes from which screen you're trusted to open.
  • PDF export (jsPDF + autotable) turns live Firestore data into an offline report for record‑keeping — a deliberately separate, exportable copy of the truth.
LIKELY QUESTION FROM THE PANEL

"What stops an admin action from silently breaking what the customer or waiter sees?"

Nothing here writes to a private "admin copy" of the data — approving an order updates the exact same orders document the customer's tracker and the waiter's queue are already listening to. There's one shape of truth per order; admin just has the widest set of screens allowed to change it.

Georginia Kioko

THE DELIVERY FLOOR — WAITER OPS & ENTRY POINT

waiter.html index.html

LIVE DEMO — DO THIS ON STAGE

  1. Open index.html first and let the audience watch it redirect straight into the app — a one‑line explanation of why a routing entry point exists at all.
  2. Open waiter.html, pick a waiter identity from the list, and enter the floor view.
  3. Show that only Approved and Dispatched orders appear here — nothing Pending, nothing from the menu or analytics side.
  4. Mark an order Dispatched, then Delivered, and point back to Esther's screen updating live in response.
  5. Show timeAgo() ticking up on an order card to demonstrate how long it's been waiting.

EXPLAIN THIS

  • index.html is a deliberate front door: a meta‑refresh into dashboard.html, so the project always has one obvious starting point instead of four scattered files.
  • Waiter identity isn't a login — it's a lightweight picker over the waiters collection, kept simple because the real gatekeeping already happened at login.html.
  • The order query here is scoped with where("status","in",["Approved","Dispatched","Delivered"]) — a waiter physically cannot see an order that hasn't been approved yet, by design, not convention.
  • This is the smallest screen in the whole system on purpose: fewer buttons on the floor means fewer chances to tap the wrong one mid‑rush.
LIKELY QUESTION FROM THE PANEL

"If picking a waiter identity isn't a real login, what's stopping anyone from opening this page and marking orders as delivered?"

For this stage of the build, waiter.html is treated as a trusted, staff‑only device sitting at the delivery point — the same assumption a physical order‑ticket rail makes. The identity picker exists to route orders to the right person, not to gate access. The natural next step, which we'd flag as future work, is folding waiter accounts into Firebase Authentication the same way customers already work, so the picker becomes a real login.

THE ENGINE ROOM — FIREBASE & BACKEND LOGIC

index.js

This is the ticket that ties every other presenter's section back together — the shared Firebase project underneath all four apps, and the one file none of the other apps are allowed to touch directly: the server‑side payment verifier.

LIVE WALKTHROUGH — DO THIS ON STAGE

  1. Open index.js and point out it runs on Firebase Cloud Functions — Google's servers — never in the customer's browser.
  2. Point at the same firebaseConfig object appearing in login, register, dashboard and admin — one project, four doors.
  3. Trace the payment path out loud: Paystack popup → reference → verifyPaymentServerSide() → this Cloud Function → Paystack's own /transaction/verify endpoint → back to Firestore.
  4. Show where the secret key actually lives: defineSecret("PAYSTACK_SECRET_KEY"), pulled from Firebase Secret Manager at run time — never in source, never in git.

EXPLAIN THIS

  • Paystack gives every project two keys: a public key, safe to ship in dashboard.html because the checkout popup is designed to be called from a browser — and a secret key that can charge, refund, and move money, which must never reach a browser.
  • Anyone can open dev tools and read a page's source. If the secret key were in dashboard.html, it would be public the moment the site shipped — that's the entire reason this function exists.
  • The function doesn't just check "did it succeed" — it re‑checks the amount against what the order should cost, which stops someone from tampering with the price in the browser before the popup opens.
  • This is defense in depth: the app already works without this function deployed (orders just get flagged unverified, see Esther's ticket) — verification is a second, independent layer, not a single point of failure.

THE VERIFICATION PATH, END TO END

Browser: Paystack popup → reference returned → Cloud Function (server) → Paystack /verify API → amount re‑checked → Firestore: order marked Paid
LIKELY QUESTION FROM THE PANEL

"Couldn't a user just fake a browser message saying their payment succeeded, without paying?"

Without this function, technically yes — the browser could claim success on its own. That's exactly the gap it closes: the frontend's claim is never trusted by itself. The Cloud Function asks Paystack directly, server‑to‑server, using a key the browser never sees, whether that specific transaction reference really succeeded and for the right amount. Trust moves from "the browser said so" to "Paystack itself confirmed it."
